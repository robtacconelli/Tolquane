# FastFlow versus Tolquane: the measurement protocol

Two implementations of the same benchmarks, one in C++ on FastFlow, one in Python on
Tolquane, on the same machine, with the same items, the same amount of work per item,
and the same way of counting. Every number in the paper comes from a JSON file that one
of the two runners wrote; nothing is typed in by hand.

## The machine and the software

Recorded by each runner into every result file: CPU model, cores and threads, memory,
kernel, compiler or interpreter and version, framework version, the date. This machine:
AMD Ryzen 7 5700, 8 cores, 16 threads, 61 GB, Linux 6.17, g++ 15.2 with `-O3
-march=native -std=c++20`, CPython 3.13 (GIL) and 3.14t (free-threaded), Tolquane 1.3.2,
FastFlow at commit d476f66 (June 2026).

## Timing rules

- Every configuration is run 5 times; the JSON keeps all five and the paper uses the
  median. A run measures wall time from the first item entering the graph to the last
  item leaving it (`time.perf_counter` / `std::chrono::steady_clock`); graph
  construction and thread start-up are inside the measured interval, since a user pays
  them too, and are also reported separately as `startup_seconds` where measurable.
- The machine is otherwise idle; runners refuse to start when the 1-minute load average
  is above 2.
- The sequential baseline of every benchmark is the same work in a plain loop of the
  same language with no framework: `seq_seconds`. Speedup is `seq_seconds / seconds`;
  efficiency is speedup divided by the number of workers.
- Items are the same values on both sides: 64-bit integers `0..N-1`, or the same file
  chunks, or the same arrays.

## The unit of work

`work(x, iters)` is the same function in both languages: starting from `x`, `iters`
rounds of `x = (x * 6364136223846793005 + 1442695040888963407) mod 2^64; x ^= x >> 13`,
returning `x`. Python does it with `& 0xFFFFFFFFFFFFFFFF`; C++ with `uint64_t`. It has
no memory traffic, cannot be vectorised, and its cost per round is stable.

A grain `G` in microseconds is turned into `iters` by calibration at the start of a run:
time `work(1, iters)` sequentially with doubling `iters` until one call takes at least
50 ms, then `iters = round(iters * G / measured_us)`. The calibrated `iters` and the
measured per-item time are written into the JSON, and the paper plots against the
measured grain, never the requested one. The grains: 0 (no work: pass the item on),
1, 10, 100, 1000 µs.

## Micro-benchmarks

| id | graph | items | what it isolates |
|---|---|---|---|
| M1 pipeline | source → stage → stage → sink, every stage passes the integer on | 1,000,000 | per-item channel cost through three hand-offs |
| M2 farm | source → farm(W workers, each `work(x, iters)`) → sink | 200,000 at G ≤ 10 µs, 20,000 at 100 µs, 4,000 at 1,000 µs | speedup against grain and worker count: W ∈ {1, 2, 4, 8, 16} |
| M3 ordered | M2 with output in input order, W = 8, G = 100 µs | 20,000 | the cost of ordering |
| M4 all-to-all | source → 4 left workers (work) → 4 right workers (work) → sink, G = 100 µs on both | 20,000 | the shuffle |
| M5 feedback | source → farm(4) with a collector that sends each item back twice before letting it out, G = 50 µs per pass | 20,000 items, 3 passes each | loops and their termination |
| M6 latency | source → farm(W) where each item sleeps 20 ms (a stand-in for a network call) | 2,000 | many waits at once: W = 8 threads, W = 200 threads (C++ and Python), and Tolquane's coroutine pool of 200 |

FastFlow runs M1 to M5 in its default non-blocking mode and again in blocking mode
(`blocking_mode(true)`); both are reported. Tolquane runs on threads with the default
batch of 32 and with batch 1, on 3.13 and on 3.14t; M2 also with the processes runtime
on 3.13. The sequential baseline of M1 is a `for` loop that calls the three stage
functions; of M2 to M5, the same loop with `work`.

## Applications on real data

Each is implemented in the natural style of its language, sequentially and on the
framework with W = 8 workers, and the code is counted in lines (blank and comment lines
excluded) as a second result. Data lives in `/mnt/1T/home/st4ck/.cache/data` here;
`data.py` fetches or generates it deterministically so anyone can reproduce it.

| id | task | data | parallel shape |
|---|---|---|---|
| A1 word count | count word frequencies with a hash map, merge the maps | `enwik8`, 100 MB of Wikipedia text (md5 a1fa5ffddb56f4953e226637dabbb36a) | 1 MB chunks split at a newline → farm(8) → one merging sink |
| A2 CSV totals | sum `amount` per `region` over a CSV | `sales.csv`, 10,000,000 rows generated by `data.py` from a fixed seed: `region,product,amount` | 4 MB chunks → farm(8) → merge |
| A3 rows | normalise each row of a float32 matrix by its L2 norm | a 20,000 × 1,000 float32 matrix from a fixed seed | scatter each block of 500 rows across 8 workers, gather |
| A4 hashes | SHA-256 of every 64 KB block of a file, ten times each | `enwik8` | blocks → farm(8) → sink counting bytes |

C++ uses `std::unordered_map`, `std::from_chars`, plain loops on `float` arrays and a
small SHA-256 (or OpenSSL if present, stated in the JSON). Python uses
`collections.Counter`, `str.split`, numpy on views, and `hashlib`. That is the point of
A3 and A4: where Python's work is done by C underneath, the framework is all that
differs. A1 and A2 show the other case, where the work itself is interpreted.

## Result files

`benchmarks/compare/results/<framework>-<host>-<date>.json`, one file per runner
invocation, a list of records:

```json
{"bench": "M2", "framework": "tolquane", "language": "python", "interpreter": "3.13.7",
 "runtime": "processes", "batch": 32, "mode": null, "workers": 8, "items": 20000,
 "grain_us_requested": 100, "grain_us_measured": 101.4, "iters": 1730,
 "seconds": [..5 values..], "seq_seconds": [..5 values..], "startup_seconds": 0.012,
 "lines_of_code": null, "notes": ""}
```

`machine.json` next to them describes the host. `analyze.py` reads every file, checks
that both sides ran the same `(bench, items, grain, workers)` sets, and writes the
tables (`tables/*.tex`, `tables/*.md`) and figures (`figures/*.pdf`, `*.png`) the paper
includes: per-item overhead, speedup against workers per grain, time against grain at
W = 8 for both languages with the crossover marked, efficiency, the applications table.

## What is not compared, and why

FastFlow's distributed runtime needs cereal and MTCL, which are not built here; the
paper reports Tolquane's TCP numbers on their own and says so. GPU offloading and
FastFlow's macro-dataflow, task-farm and pool-evolution patterns have no Tolquane
counterpart yet. Neither side is tuned beyond its documented options; no core pinning,
no huge pages, no `mapping_string.sh`.
